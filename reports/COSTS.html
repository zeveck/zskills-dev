Z Skills — Cost Estimate

An estimate of what it would cost to build Z Skills via the Claude API at published list prices, computed from per-API-response token counts in Claude Code session JSONL transcripts.

Actual out-of-pocket cost was much lower. The development happened on a Claude Max x20 plan ($200/mo) plus some overflow usage spend — not at API list prices. The figures here are the list-price API equivalent: useful as a benchmark for someone reproducing this work via direct API calls, not a record of what was actually paid.

Methodology

Rate source

All rates fetched 2026-05-21 from Anthropic's published API pricing page (platform.claude.com/docs/en/about-claude/pricing) and unchanged through the 2026-06-01 refresh:

Claude Opus 4.7  → $5 input / $25 output / $6.25 5m-CW / $10 1h-CW / $0.50 CR per MTok
Claude Opus 4.8  → $5 input / $25 output / $6.25 5m-CW / $10 1h-CW / $0.50 CR per MTok
Claude Haiku 4.5 → $1 input / $5 output  / $1.25 5m-CW / $2  1h-CW / $0.10 CR per MTok

The prior Opus generation (4.0 and 4.1) is listed at 3× these rates — the Opus 4.5+ pricing tier took effect with the Opus 4.5 release on 2025-11-24. Equivalent work done at those older rates would have cost roughly 3× as much (~$37k logged-only, ~$48k including the projected 4.6 era). Z Skills development used Opus 4.6 in the unlogged pre-2026-04-18 era, Opus 4.7 from 2026-04-18 through 2026-05-28, and a mix of Opus 4.7 + 4.8 from 2026-05-29 onward; all bill at the Opus 4.5+ tier above.

Per-response token totals (the unit of billing)

Scanned 2,070 JSONL files across 6 project working directories (~/.claude/projects/-workspaces-zskills/ + 5 ~/.claude/projects/-tmp-zskills-*/ ephemeral worktree-spawned dirs). The 2026-05-21 snapshot scanned 8 dirs; two of those -tmp-zskills-* dirs have since been cleaned off disk. Claude Code splits each API response into multiple JSONL records — one per content block (thinking, text, tool_use) — and each record carries the full per-response usage object. The Anthropic API bills per response, not per content block, so token totals are computed by deduplicating against message.id (one ID = one API response = one bill). For output_tokens, which streams cumulatively, the max value across a response's records is used (per Anthropic's streaming docs: "token counts shown in the usage field of the message_delta event are cumulative"). For input_tokens, cache_read_input_tokens, and cache_creation (5m / 1h), values are constant across all records of a given message.id (verified empirically: 100% match across the multi-record message.ids in the corpus).

Cache-tier split comes from usage.cache_creation.ephemeral_5m_input_tokens and usage.cache_creation.ephemeral_1h_input_tokens; the flat cache_creation_input_tokens field agrees with the decomposed total on >99.99% of records (5 records disagree by ~5k tokens each, immaterial). Records with message.model containing "synthetic" are excluded as non-API turns.

Multipliers applied

  • Data residency: 1.0× (default global routing assumed; not US-only).
  • Fast mode: 1.0× (never used in this development).
  • Batch API: 1.0× (interactive sessions, no batch discount).
  • 1M context window: 1.0× per Anthropic — "Opus 4.7, Opus 4.6, and Sonnet 4.6 include the full 1M token context window at standard pricing."
  • Extended thinking: not separately metered; output_tokens already includes thinking-mode generation. JSONL stores only the cryptographic signature of redacted thinking blocks, not their text, but the API's reported output_tokens count is faithful to what was generated and billed.

What this doesn't measure

Pre-2026-04-18 development (~23 days, ~1/3 of project elapsed time) has no JSONL transcripts — its cost is estimated, not measured (see the Opus 4.6 section above for the derivation). Genuinely excluded from every figure on this page: wall-clock time, human review effort, Claude.ai chat sessions for architecture discussion outside Claude Code, and the pre-repo prototyping that fed the initial commit. Real billing depends on contract, any volume discounts, and other terms; the numbers above are at published list prices.

Verification

The per-API-response billing methodology was checked through internal consistency checks. These confirm the JSONL data is being read correctly — not that the JSONL itself matches a third-party billing record (none available since development ran on the Claude Max subscription, not direct API billing).

  • API semantics. Anthropic's streaming-API documentation states that the usage object is emitted once per API response (not per content block), with output_tokens reported cumulatively across each response's message_delta events.
  • Field-by-field consistency. Across the multi-record message.ids in the corpus, input_tokens, cache_read_input_tokens, and cache_creation tier values are 100% constant within each message.id (per-response data), confirming they should be counted once per response, not once per content block.
  • Cross-file uniqueness. No message.id appears in more than one JSONL file across the 2,070 scanned, so dedup-by-message.id doesn't over- or under-count across the parent-session/subagent split.
  • Manual trace. Twenty randomly-sampled message.ids were inspected by hand; every multi-record entry resolved to either a content-block split within a single API response (thinking + text + tool_use blocks) or a session-resume duplicate (Claude Code re-writes prior turns when a session is resumed). Dedup-by-message.id handles both.
  • End-to-end session walk. A short session was read line-by-line: by-eye counted 5 distinct assistant API responses across 9 usage-bearing JSONL records. Dedup-by-message.id returned 5 — exact match against the by-hand count.
  • Three arithmetic methods. Aggregate-first, per-record-of-deduplicated-set, and per-day re-aggregation all reproduce the grand total to the cent.
  • Outlier check. Sampled message.ids where reported output_tokens looked disproportionate to visible content all traced to redacted extended-thinking blocks — Claude Code stores only the cryptographic signature of those blocks, not the thinking text itself.
